# poly_hourly_kit_eth — часовая модель ETH под рынок Polymarket

Комплект для подключения обученной модели к часовым рынкам Polymarket
«Ethereum Up or Down». Внутри: сама модель, код расчёта признаков, одна функция
для прогноза, самопроверка и код переобучения.

Комплект самодостаточен. Ему не нужен ни исходный исследовательский проект,
ни какой-либо код за пределами этой папки.

> **Если у вас уже есть комплект по BTC** — прочитайте раздел 10. Код признаков
> у них общий и это доказано контрольной суммой, но модель, фикстуры и пара
> здесь свои. И, что важнее всего, **исходы BTC и ETH сильно связаны**: ставки
> по обеим монетам в один час риск не делят, а складывают. Раздел 11.

## Первые пять минут

```bash
python -m venv .venv
.venv\Scripts\activate          # Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
python -m kit.selfcheck
```

Самопроверка обязана напечатать **ПРОВЕРКА ПРОЙДЕНА**. Это первое, что нужно
сделать: она берёт 200 часов, посчитанных на нашей машине настоящим прогоном,
и пересчитывает их у вас — минутки, обрезка, свечи, 22 признака, вероятность.
**Допуск ноль**: любое расхождение означает, что что-то подключено не так, и
лучше узнать об этом сейчас, чем по деньгам через месяц.

Дальше — один вызов:

```python
from kit.predict import predict

ans = predict(minutes_df, "2026-09-06 22:00")
# {'p_up': 0.4851794105082115,
#  'side': 'Down',
#  'model_id': '0c00b88058b1',
#  'decision_time_utc': '2026-09-06T21:58:00+00:00',
#  'feature_hour_utc':  '2026-09-06T21:00:00+00:00'}
```

Пример не выдуман: `2026-09-06 22:00` — последний час фикстуры комплекта,
и такой же ответ вы получите на своей машине.

`predict` — единственная публичная функция комплекта. Всё остальное намеренно
спрятано: чем меньше способов позвать модель, тем меньше способов позвать её
неправильно.

## 1. На какой вопрос отвечает модель

> Закроется ли часовая свеча Binance ETHUSDT за час H **не ниже** своего открытия?

Формально: `close >= open` полной часовой свечи. **Равенство засчитывается в Up** —
именно так написано в правиле резолва Polymarket («greater than or equal»).

Это не «вырастет ли цена». Это ровно то условие, по которому рынок резолвится.
Разница мелкая, но она есть: за три года набралось 16 часов из 26 280, где цена
закрытия совпала с ценой открытия.

## 2. Тайминг — с точностью до минуты

```
H-1:00  ─┬─ начинается свеча признаков
         │
H-1:57  ─┤  последняя минутка, которая идёт в признаки
         │
H-1:58  ─●  МОМЕНТ РЕШЕНИЯ: здесь вызывается predict(df, H)
         │
H-1:59  ─┤  эти две минуты модель НЕ видит
H:00    ─┴─ начинается час рынка H, его исход и предсказываем
```

- **Решение принимается в H минус 2 минуты.**
- **Признаки считаются по свече H−1, собранной из минуток `:00 .. :57`** —
  58 минуток из 60. Последние две отброшены, потому что в момент решения их
  ещё не существует.
- Час рынка `H` передаётся в `predict` как есть, ровным началом часа. Момент
  решения и час признаков функция вычисляет сама и возвращает в ответе — сверьте
  их с расписанием своего планировщика при первом запуске.

**Отклонение от этого тайминга делает все измеренные ниже числа
недействительными.** Модель обучена на свечах, обрезанных ровно на 2 минуты.
Дадите ей полную свечу H−1 — она получит на вход то, чего в бою не бывает,
и померенное качество к такому режиму отношения не имеет.

Обратное тоже верно: решать сильно раньше, чем за 2 минуты, нельзя по той же
причине. Если ваш планировщик успевает только за 3-4 минуты, это отдельный
вопрос, который надо мерить заново, а не считать, что «примерно то же самое».

`predict` сама отрезает всё, что позже момента решения. Передать минуток больше,
чем нужно, безопасно; заглянуть в будущее — невозможно даже намеренно.

## 3. Какие нужны данные

**Минутные бары Binance ETH/USDT (спот, символ ETHUSDT).**

`minutes_df` — `pandas.DataFrame`:

| что | требование |
|---|---|
| индекс | `DatetimeIndex`, время **открытия** минутки, UTC (наивное время трактуется как UTC) |
| колонки | `open`, `high`, `low`, `close`, `volume`, `trades` |
| порядок | любой — функция отсортирует; но дубликаты меток времени запрещены |

Колонка **`trades`** (число сделок внутри минутки) обязательна: по ней считается
признак `trrel`. У Binance это девятое поле ответа `/api/v3/klines`
(`number_of_trades`). Без неё модель работать не может — это не опция.

### Сколько нужно истории

| | часов | суток |
|---|---|---|
| **Жёсткий минимум** (меньше — исключение) | **240** | 10 |
| **Рекомендуется** | **720** | 30 |

Откуда 240. Самому длинному окну признаков (`z168`, `vol_ratio`) нужно
169 часовых свечей. Сверх того признак `streak_signed` формально смотрит на всю
историю сразу — практически же самая длинная серия одинаковых по знаку свечей
короткая. 240 взяты с запасом к порогу в 169 часов, 720 — чтобы запас был и у вас.

Лишнюю историю передавать не вредно: функция отрежет её сама.

### Дыры в данных

`predict` откажется считать и объяснит, чего не хватает, если:

- истории меньше 240 часов;
- внутри окна истории есть час, за который нет **ни одной** минутки;
- час признаков H−1 собран меньше чем из 50 минуток (из 58).

Это сделано намеренно. Пропустить час дешевле, чем поставить вслепую, поэтому
приблизительного ответа функция не возвращает никогда — только число или
исключение с внятным текстом.

Дыры у ETH бывают: за семь лет истории нашлось **43 часа**, за которые у Binance
нет ни одной минутки. Это простои биржи, а не потеря данных с нашей стороны.

## 4. Как читать ответ

```
p_up > 0.5   ->  ставим Up
p_up <= 0.5  ->  ставим Down
```

Поле `side` уже содержит готовый ответ, считать ничего не надо.

### Порога уверенности нет. Ставим на каждый час.

Это не упущение, а измеренный результат. Отбор часов по уверенности проверялся
честно — порог выбирался внутри обучающего окна, проверочная часть его не видела.
Вот что вышло за три года при ставке 5 шейров по 0.50:

| Режим | Ставок | Точность | Итого без комиссии |
|---|---|---|---|
| **Каждый час** | 26 280 | 54.04 % | **+5 315 $** |
| Только уверенные (20.8 % часов) | 5 460 | 57.55 % | +2 060 $ |

Точность при отборе действительно растёт — с 54.04 % до 57.55 %. Но ставок
остаётся пятая часть, и в деньгах отбор проигрывает больше чем вдвое.
Поэтому: **ставим на каждый час, порога не вводим.**

> **Про поле `threshold` в паспорте модели.** В `model/poly_hourly_eth.json` есть
> `"threshold": 0.58`. Это наследство исследовательского проекта, где экономика
> другая (спот, выигрыш пропорционален движению цены). **На этом рынке его
> использовать не надо.** Оно оставлено в паспорте только чтобы файл не
> расходился с оригиналом.

## 5. Экономика

Polymarket — не спот. Шейр покупается за цену `p`, выигравший гасится за 1 $,
проигравший за 0 $. Поэтому **точка безубыточности численно равна цене входа**:
купил по 0.50 — нужно больше 50 % угаданных.

| Режим исполнения | Точность безубыточности |
|---|---|
| **Мейкером** (пассивная лимитка, комиссии нет) | **50.00 %** |
| **Тейкером** (пересекли стакан) | **51.75 %** |

Комиссия тейкера считается как `shares × 0.07 × p × (1−p)` и берётся с каждой
ставки — уверены мы или нет. При 5 шейрах по 0.50 это 0.0875 $ за ставку.

За три года: **+5 315 $** без комиссии, **+3 015 $** с комиссией тейкера.
Оба числа положительные — но второе получено при допущении, что нас всегда
наливают, см. раздел 8.

### Потолок цены входа: 0.55

**Выше 0.55 не покупать.**

Наклон калибровки модели — **0.8064**. Единица означала бы «обещала 60 % —
сбылось 60 %». Меньше единицы означает, что модель переуверена: обещанному
числу верить нельзя буквально, реальный потолок ниже обещанного.

Потолок посчитан на данных этой модели, а не взят у BTC. Берём все часы, где
модель обещает своей стороне не меньше `P`, и смотрим, сколько на самом деле
сбылось. Безубыточность равна `P`, поэтому колонка «запас» — это и есть прибыль:

| Цена входа P | Ставок | Доля часов | Сбылось | Интервал Уилсона | Запас к P | Запас по нижней границе |
|---|---|---|---|---|---|---|
| 0.50 | 26 280 | 100.0 % | 54.04 % | 53.44–54.65 | +4.04 п.п. | +3.44 п.п. |
| 0.52 | 19 959 | 75.9 % | 54.89 % | 54.20–55.58 | +2.89 п.п. | +2.20 п.п. |
| 0.54 | 13 922 | 53.0 % | 55.41 % | 54.58–56.23 | +1.41 п.п. | +0.58 п.п. |
| **0.55** | **11 213** | **42.7 %** | **56.08 %** | **55.16–56.99** | **+1.08 п.п.** | **+0.16 п.п.** |
| 0.56 | 8 616 | 32.8 % | 56.75 % | 55.71–57.80 | +0.75 п.п. | **−0.29 п.п.** |
| 0.57 | 6 364 | 24.2 % | 57.79 % | 56.58–59.00 | +0.79 п.п. | −0.42 п.п. |
| 0.58 | 4 485 | 17.1 % | 58.42 % | 56.97–59.85 | +0.42 п.п. | −1.03 п.п. |
| 0.60 | 1 812 | 6.9 % | 59.11 % | 56.83–61.35 | **−0.89 п.п.** | −3.17 п.п. |
| 0.62 | 526 | 2.0 % | 58.56 % | 54.30–62.69 | −3.44 п.п. | −7.70 п.п. |

Читать так: по среднему значению покупка остаётся прибыльной до 0.58 и уходит
в минус на 0.60. Но по **нижней границе интервала** запас исчезает уже
на 0.56. **0.55 — последняя цена, где даже нижний край интервала выше
безубыточности**, поэтому потолком взята она, а не 0.58.

При фиксированной цене входа 0.50 переуверенность не мешает вовсе: там нужен
только знак отклонения от монетки. Но поднимать цену входа вслед за высоким
`p_up` — прямой путь в минус.

## 6. Измеренные числа

Walk-forward: скользящее обучение 1460 дней → зазор 7 дней → проверка 30 дней,
шаг 30 дней. Окна проверки идут встык, каждый час периода оценки предсказан
ровно один раз, модель в каждом фолде обучается с нуля.

Период оценки **2023-09-07 .. 2026-09-06**, конец данных заморожен на
**2026-09-07 00:00 UTC**.

| | Значение |
|---|---|
| Точность модели | **54.04 %**, Уилсон 53.44–54.65 |
| Точность простого правила («против предыдущей») | **52.64 %**, Уилсон 52.04–53.24 |
| **Разрыв** | **+1.40 п.п.** |
| McNemar p (парный тест на тех же часах) | **1.336e-05** |
| Часов в проверке | **26 280** |
| Фолдов | **37** |
| Окон выше 50 % | **36 из 37** |
| Движение за сделку | +0.53 ±0.83 б.п. |
| Balanced accuracy | 54.00 % |
| ROC-AUC | 0.5524 |
| Log loss / Brier | 0.689163 / 0.248010 |
| Наклон калибровки | 0.8064 |

### С чем сравнивается

Простое правило — не формальность, а настоящий конкурент. Все правила считаются
по **обрезанной** свече H−1 и по рыночному правилу `close >= open`: в момент
решения исход полной свечи H−1 ещё неизвестен.

| Стратегия | Точность | Интервал Уилсона | б.п. за сделку |
|---|---|---|---|
| всегда Up | 50.72 % | 50.11–51.32 | +0.39 |
| всегда Down | 49.28 % | 48.68–49.89 | −0.39 |
| повтор предыдущей (моментум) | 47.36 % | 46.76–47.96 | +0.08 |
| **против предыдущей ← планка** | **52.64 %** | 52.04–53.24 | −0.08 |
| против 2 одинаковых подряд | 52.27 % | 51.67–52.88 | +0.62 |
| **модель** | **54.04 %** | **53.44–54.65** | **+0.53** |

Планкой взято **лучшее** из простых правил на барах самой ETH, а не самое
удобное. У BTC лучшее правило другое — «против 2 одинаковых подряд»; против него
разрыв был бы **+1.77 п.п.** (p = 1.575e-07), то есть красивее. Взято строгое
сравнение, а не льстивое.

Сравнивать доверительные интервалы двух точностей нельзя — они пересекаются
даже при настоящей разнице. Поэтому значимость берётся парным тестом Макнемара
на одних и тех же часах.

### По фазам рынка

| Фаза | Часов | Правило | Модель | Разрыв | McNemar p | б.п. модели |
|---|---|---|---|---|---|---|
| медвежья | 14 160 | 52.56 % | 53.61 % | +1.05 п.п. | 0.01801 | +0.13 |
| боковик | 3 144 | 52.99 % | 53.59 % | +0.60 п.п. | 0.5328 | +0.02 |
| бычья | 8 976 | 52.64 % | 54.89 % | +2.25 п.п. | 4.856e-05 | +1.34 |

**Ни одна фаза не проваливается** — модель обгоняет правило во всех трёх.
Внутри отдельной фазы интервал шире, поэтому парный тест значим не везде;
значимость берётся с пула всех часов, а разбивка нужна, чтобы поймать провал,
а не чтобы доказать преимущество трижды.

О самой разметке фаз — важная оговорка в разделе 12.

### Оговорка, которую надо прочитать: перевес слабеет по годам

| Год | Часов | Правило | Модель | Разрыв | б.п. модели |
|---|---|---|---|---|---|
| 2023 | 2 784 | 53.92 % | 53.99 % | +0.07 п.п. | +0.14 |
| 2024 | 8 784 | 53.59 % | 55.67 % | **+2.08 п.п.** | +1.82 |
| 2025 | 8 760 | 51.38 % | 53.20 % | +1.82 п.п. | +0.10 |
| **2026** | 5 952 | 52.50 % | 52.92 % | **+0.42 п.п.** | **−0.57** |

В 2026 году перевес над простым правилом — **+0.42 п.п.**, заметно меньше
среднего по периоду и внутри погрешности отдельно взятого года. Хуже того,
**движение за сделку в 2026 ушло в минус (−0.57 б.п.)** при формально
положительной точности: модель угадывает чуть чаще, но выигрывает по мелочи и
проигрывает крупнее. Это может быть шумом, а может быть затуханием сигнала;
на этих данных одно от другого не отличить.

Планируйте исходя из того, что перевес ближе к нижней границе, а не к средней,
и следите за живым журналом прогнозов.

### Чего эти числа не доказывают

1. **Что лимитка по 0.50 исполнится.** Весь расчёт предполагает, что нас налили.
   По историческим свечам это не проверить — ответ дадут только живые сделки.
2. **Что нас наливают не тогда, когда мы неправы.** Отбор по заполнению — главный
   риск стратегии, и в этих числах он не учтён вовсе.
3. **Что сигнал сохранится в будущем.** Граница знаний модели — 2026-09-06 21:00 UTC.
   Настоящая проверка — прогнозы вперёд после этой даты.
4. **Что число проверенных гипотез учтено.** ETH — одна из двух монет, на которых
   проверялся замороженный рецепт BTC. На второй значимого перевеса не нашлось,
   и её комплект не собирался. Будь монет двадцать, одна показала бы «значимо»
   случайно — на двух это учесть нечем, кроме как знать об этом.

## 7. Чего не делать

**Не применять к 5- и 15-минутным рынкам Polymarket.** Они резолвятся по
**Chainlink**, а не по свече Binance. Это другой источник цены с другой
агрегацией и другими моментами фиксации. Модель обучена на правиле
«свеча Binance», и на этих рынках её числа не значат ничего.

**Не подставлять эту модель под BTC, а модель BTC — под ETH.** Файл признаков
у них общий, поэтому технически ничего не сломается и ошибки вы не увидите —
получите молча неверные числа. Модель обучена на движениях ETH.

**Не считать ставки по BTC и ETH независимыми.** Раздел 11. Это самая дорогая
из возможных ошибок при работе с двумя комплектами сразу.

**Не менять обрезку.** Минутки `:00..:57` — часть модели, а не настройка.
Дадите полную свечу или обрежете на другую величину — получите другую модель
без измеренного качества.

**Не добавлять порог уверенности.** Проверено, в деньгах проигрывает (раздел 4).
Ставим на каждый час.

**Не поднимать цену входа вслед за высоким `p_up`.** Модель переуверена,
наклон калибровки 0.8064, потолок — 0.55 (раздел 5).

**Не править `kit/features.py`.** Файл побитово совпадает с тем, на котором
обучена модель, и его контрольная сумма проверяется при каждом импорте. Любая
правка — даже переставленный пробел — делает модель другой.

## 8. Как заменить модель на новую версию

Положить два файла в `model/`:

```
model/poly_hourly_eth.txt     сама модель
model/poly_hourly_eth.json    её паспорт (в нём sha256 файла .txt)
```

**Кода трогать не нужно.** Оба файла берутся из одного комплекта: при загрузке
сверяется контрольная сумма, и .txt от одной версии с .json от другой работать
не будет — вы получите понятную ошибку, а не тихо неверный прогноз.

После замены пересоберите эталон самопроверки — он привязан к конкретной модели:

```bash
python -m train.make_fixtures
python -m kit.selfcheck
```

### Переобучение своими силами

```bash
python -m train.retrain
```

Одна команда: грузит минутки, прогоняет тот же walk-forward 1460/7/30 с теми же
гиперпараметрами, обучает боевую модель на последних 1460 днях, сохраняет её
с паспортом и печатает таблицу «было / стало» рядом с числами прежней модели.

#### Переобучение даёт близкие числа, но не те же самые. Так и должно быть.

Модель, лежащая в `model/`, обучена исследовательским кодом проекта. `train/`
в этом комплекте — тот же рецепт, но самостоятельная, урезанная реализация.
Разница между ними измерена и составляет **ровно одну строку обучения**:

| | Модель в комплекте | `python -m train.retrain` |
|---|---|---|
| Баров обучения | 35 037 | **35 038** |
| Баров проверки | 26 280 | 26 280 |
| Планка | 52.6408 % | **52.6408 %** |
| Точность модели | 54.04 % | 53.89 % |
| Разрыв | +1.40 п.п. | +1.25 п.п. |

Планка, число баров, границы окна и порог совпадают **точно**. Отличается один
час: исследовательский код дополнительно выбрасывает час, за которым следующий
бар идёт не ровно через час (дыра в данных биржи), а `train/` этого не делает.

Этот один час из 35 038 сдвигает результат на 0.16 п.п. Так бывает: при
`subsample = 0.8` состав подвыборок зависит от числа строк, и деревья вырастают
слегка другими. Это не ошибка и не признак нестабильности сигнала — это цена
того, что `train/` не тащит за собой весь исследовательский проект.

**Что из этого следует практически.** Если после переобучения вы увидите разрыв
не +1.40, а, скажем, +1.25 п.п. — это нормально, а не поломка. Тревожиться стоит,
если разрыв уйдёт около нуля или станет отрицательным, либо если провалится
какая-то из фаз рынка: об этом `retrain` напишет отдельной строкой.

По умолчанию новая модель кладётся в `model_new/` и **ничего не заменяет** —
решение остаётся за вами. Заменить сразу и пересобрать фикстуры:

```bash
python -m train.retrain --replace
```

Полезные флаги: `--cache-dir` (кэш минуток; можно указать на готовый — тогда
качать нечего), `--out` (куда положить результат), `--data-end`.

**Про `--data-end`.** По умолчанию грузится всё до текущего момента. Числа,
переданные с этим комплектом, получены при `--data-end "2026-09-07 00:00"`.
Без этой заморозки каждый следующий запуск приносит на минуту больше данных,
и результат слегка плывёт между прогонами. Хотите воспроизвести наши числа —
задайте её явно.

Первый запуск качает около 180 МБ минутных архивов с `data.binance.vision`
и `api.binance.com`. Ключи API не нужны, всё публичное. Дальше кэш на диске.
Сам прогон — около 20 секунд.

## 9. Чего в комплекте нет

Это зона напарника, и она намеренно не тронута:

- подключение к бирже и к Polymarket, ключи, кошельки, авторизация;
- выставление и отмена ордеров, работа со стаканом, контроль исполнения;
- отслеживание резолва рынков и расчёт фактического P&L;
- риск-менеджмент: размер ставки, лимиты просадки, аварийная остановка;
- планировщик, который вызывает `predict` в H−2 минуты;
- мониторинг, журналы, оповещения.

Комплект отвечает ровно на один вопрос: какая вероятность у Up на ближайший час
и с какой стороны ставить. Всё, что вокруг этого, — ваше.

## 10. Чем этот комплект отличается от комплекта BTC

| | BTC | ETH |
|---|---|---|
| Пара | биткойн | **ETHUSDT** |
| Код признаков | `kit/features.py` | **тот же файл, байт в байт** |
| Модель | `ca2589be653a` | **`0c00b88058b1`** |
| Фикстуры | свои 200 часов BTC | **свои 200 часов ETH** |
| Планка | «против 2 одинаковых подряд», 52.58 % | **«против предыдущей», 52.64 %** |
| Точность модели | 53.65 % | **54.04 %** |
| Разрыв над планкой | +1.07 п.п. | **+1.40 п.п.** |
| McNemar p | 0.0016 | **1.336e-05** |
| Окон выше 50 % | 37 из 37 | **36 из 37** |
| Наклон калибровки | 0.756 | **0.8064** |

### Код признаков — тот же самый, и это доказано, а не заявлено

`kit/features.py` в этом комплекте **побитово совпадает** с `kit/features.py`
комплекта BTC. Контрольная сумма обоих файлов:

```
685ed4d6fd468f494fd3a13e7325a78a00f57eaa3f51cbff4ee3ad1b3ccbc951
```

Она записана в `passport.json` и **сверяется при каждом импорте** — не как
формальность при сборке, а на каждом запуске у вас. Не совпала — расчёт
останавливается с объяснением, а не считает молча.

Так и было задумано: ETH проверялся замороженным рецептом BTC без единого
изменения признаков, схемы нарезки, гиперпараметров и `random_state`. Если бы
признаки подбирались под ETH заново, сравнивать две монеты было бы уже нельзя.

Практическое следствие: **если вы уже подключили комплект BTC, вся ваша обвязка
подходит и сюда без изменений.** Меняются только папка, символ пары и файл
модели.

### Что отличается в коде

- `train/binance_1m.py`: `SYMBOL = "ETHUSDT"`.
- `train/retrain.py`: планка — «против предыдущей», а не «против 2 одинаковых
  подряд». Это не косметика: планка обязана быть лучшим простым правилом самой
  монеты, иначе таблица «было / стало» сравнивала бы с чужим числом.
- Пути к модели: `model/poly_hourly_eth.*`.

Всё остальное — `kit/features.py`, `kit/candles.py`, `kit/_featload.py`,
`train/validation.py`, `train/metrics.py`, `train/phases.py` — побитовые копии.

## 11. ВНИМАНИЕ: BTC и ETH — почти одна ставка, а не две

Если вы работаете и с BTC, и с ETH, это самый важный раздел документа.

Исходы двух монет измерены на одних и тех же 26 280 часах периода оценки:

| | Значение |
|---|---|
| Одинаковый ответ (обе Up или обе Down) | **81.30 %** часов |
| Интервал Уилсона | 80.83–81.77 |
| Столько было бы при независимости | 50.01 % |
| Сверх независимости | **+31.29 п.п.** |
| Коэффициент связи φ | **0.6260** |

**BTC и ETH дают одинаковый ответ примерно в четырёх часах из пяти.**

Практический вывод, который надо заложить в риск-менеджмент:

> **Ставки по BTC и ETH в один и тот же час не диверсифицируют риск, а
> складываются. Считайте размер позиции как для ОДНОЙ ставки двойного объёма,
> а не для двух независимых.**

Две «независимые» позиции по 2.50 $ при такой связи — это фактически одна
позиция на 5 $. Обычная формула «разброс делится на корень из числа позиций»
здесь неприменима: она предполагает независимость, которой нет. Просадка
приходит по обеим монетам одновременно.

Диверсификация здесь возможна **по времени, а не по инструменту**.

Отдельно: связь измерена на прошлом. Что она останется такой же — этими числами
не доказано.

## 12. ВНИМАНИЕ: разметка фаз рынка откалибрована на BTC

Разбивка по фазам в разделе 6 использует пороги, подобранные под волатильность
**BTC**: доходность ±20 % за 90 дней и просадка 25 %. У ETH амплитуда движений
больше, и та же разметка даёт **перекошенную смесь**:

| Фаза | Часов у ETH | Доля |
|---|---|---|
| медвежья | 14 160 | 53.9 % |
| боковик | 3 144 | 12.0 % |
| бычья | 8 976 | 34.2 % |

Для сравнения, у BTC на тех же порогах три фазы делятся почти поровну
(32 % / 36 % / 32 %). То есть «боковик» у ETH — это узкая полоса из 3 144 часов,
а не треть периода, и интервал на ней соответственно шире.

Что из этого следует:

- **На модель это не влияет никак.** Фаза рынка **не входит в число признаков** —
  ни в одном из 22. Это исключительно слой отчётности, разрез для чтения
  результата.
- **При чтении разбивки по фазам это надо держать в голове.** «Боковик +0.60 п.п.,
  p = 0.5328» — не признак слабости модели в боковике, а следствие того, что
  боковика по этой разметке всего 12 % часов.
- Для ETH разметку стоило бы калибровать отдельно, но это изменило бы рецепт,
  а рецепт был заморожен намеренно.

## Состав комплекта

```
README.md                 этот файл
requirements.txt          точные версии библиотек
passport.json             контрольные суммы features.py и фикстур

model/
  poly_hourly_eth.txt     модель LightGBM (текстовый формат)
  poly_hourly_eth.json    паспорт: sha256, признаки, измеренные числа, проверки

kit/                      боевая часть
  predict.py              ЕДИНСТВЕННАЯ публичная функция: predict()
  candles.py              минутки -> обрезанные часовые свечи
  features.py             22 признака; побитовая копия, править нельзя
  _featload.py            загрузка features.py со сверкой контрольной суммы
  selfcheck.py            самопроверка, допуск ноль

fixtures/
  minutes.csv.gz          минутки ETH под самопроверку
  reference.csv           200 часов: 22 признака и эталонная вероятность

train/                    переобучение (в бою не нужно)
  retrain.py              одна команда: walk-forward + модель + сравнение
  make_fixtures.py        пересборка эталона после смены модели
  binance_1m.py           загрузка минуток ETHUSDT с кэшем на диск
  validation.py           схема 1460/7/30, фолды, проверка целостности
  metrics.py              точность, б.п., Макнемар, калибровка
  phases.py               разметка фаз рынка
```

Для боевого прогноза достаточно `kit/`, `model/` и трёх библиотек
(`lightgbm`, `numpy`, `pandas`). Папка `train/` и остальные зависимости нужны
только чтобы переобучить модель.
