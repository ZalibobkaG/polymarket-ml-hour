# Как бот выставляет ордера и почему лимитка по 49 центов иногда не встаёт

Документ для команды. Разбираем три вещи: механику ордеров на Polymarket,
почему заявка отклоняется при живой встречке, и сколько денег имеет смысл
ставить по формуле Келли. В конце — полный проход по логике бота на реальных
примерах из наших логов.

---

## 1. Что вообще покупается

Часовой рынок «Bitcoin Up or Down» — это два токена, `Up` и `Down`. Один из них
после закрытия часа гасится за $1, второй за $0. Купить можно любой, цена всегда
между 0 и 1 и читается как вероятность.

При покупке `shares` штук по цене `p`:

```
выигрыш:   shares × (1 − p)
проигрыш: −shares × p
```

Отсюда главное правило, из которого дальше растёт всё остальное:

> **Точка безубыточности численно равна цене входа.**
> Купил по 49 центов — нужно угадывать 49% времени. По 55 — уже 55%.

Наша модель по walk-forward-валидации даёт **53.65%** (26 280 часов, 37 фолдов).
Значит, при входе по 0.49 у нас формально **4.65 процентных пункта запаса**.
Именно на этом держится вся конструкция.

Проверка на живых числах из базы. Час 2026-09-05 05:00, ставили `Up` × 5 по 0.49,
угадали: `+2.55$` = `5 × (1 − 0.49)`. Час 04:00, не угадали: `−2.45$` = `−5 × 0.49`.
Всё сходится до цента.

## 2. Стакан, мейкер и тейкер

В стакане две стороны:

- **bid** — по чём готовы купить (заявки покупателей);
- **ask** — по чём готовы продать (заявки продавцов).

Между лучшим bid и лучшим ask лежит спред. Мы всегда **покупаем**, поэтому нас
интересует **ask**: это цена, по которой прямо сейчас можно взять товар.

Две роли:

| | Как исполняется | Комиссия |
|---|---|---|
| **Мейкер** (пассивно) | Заявка ложится в книгу и **ждёт**, пока кто-то придёт и продаст нам | Не платим, ещё и ребейт капает |
| **Тейкер** (агрессивно) | Забираем чужую заявку, стоящую в книге, **мгновенно** | Платим комиссию |

Формула комиссии на нашей категории (Crypto):

```
комиссия на шейр = FEE_RATE × p × (1 − p)      где FEE_RATE = 0.07
ребейт мейкеру   = 0.20 × комиссия
```

Комиссия максимальна ровно в середине (при p = 0.50) и гаснет к краям. При 0.49
это 1.75 цента на шейр — на ставке в 5 шейров 8.7 цента. Немного в абсолюте, но
это **1.8 процентного пункта требуемой точности**, а весь наш запас — 4.65 пункта.
То есть комиссия съедает больше трети перевеса. Поэтому мы по умолчанию мейкеры.

Проверка на бумажной сделке 2026-09-05 07:00: взяли тейкером по 0.47, выиграли,
P&L `+2.5628$`. Считаем: `5 × 0.53 − 5 × 0.07 × 0.47 × 0.53` = `2.65 − 0.0872` =
`2.5628`. Формула подтверждена реальными данными.

## 3. Почему лимитка по 0.49 не встаёт, когда есть встречное предложение

Это главный вопрос, и интуиция здесь обманывает.

Мы отправляем ордера с флагом **post-only** (`config.POST_ONLY = True`). Это
указание бирже: *«поставь заявку в книгу; если она исполнится немедленно —
не исполняй, а отклони»*.

Теперь ключевой момент. **Лимитная заявка на покупку по 0.49 означает «куплю по
0.49 или дешевле».** Она не ждёт цены ровно 0.49 — она хватает всё, что не дороже.

Разберём на цифрах. Пусть в стакане лучший ask = 0.47.

- Мы шлём «купить по 0.49».
- Биржа смотрит: есть продавец по 0.47, а покупатель готов дать до 0.49.
  Сделка возможна → **исполняем немедленно по 0.47**.
- Но у нас стоит post-only. Мы сами запретили немедленное исполнение.
- Биржа отвечает: `invalid post-only order: order crosses book`.

Слово **crosses** — «пересекает» — здесь буквальное: наша цена покупки
пересекла чужую цену продажи. Заявка не может «просто полежать» в книге,
потому что она бы там не пролежала ни микросекунды.

### Почему нельзя «переставить на 0.48»

Частая идея: раз по 0.49 отклонили, а тейкером мы в итоге берём по 0.47 —
давайте переставим на 0.48, она же встанет.

**Не встанет.** Если ask = 0.47, то заявка «куплю по 0.48» тоже пересекает
книгу — 0.48 ≥ 0.47. Отклонят точно так же. И по 0.47 отклонят. Единственная
цена, которая ляжет в книгу — **строго ниже лучшего ask**, то есть 0.46 и ниже.
А там мы уже не покупаем по 0.49, мы покупаем по 0.46, и это другая ставка с
другой доходностью — и, главное, она может вообще не исполниться.

Схематично, при ask = 0.47:

```
0.49  → пересекает книгу  → post-only отклоняет
0.48  → пересекает книгу  → post-only отклоняет
0.47  → пересекает книгу  → post-only отклоняет
0.46  → ложится в книгу   → но ждёт, пока цена придёт к нам
```

### Так отклонение — это ошибка?

**Нет.** Post-only-отказ — это штатный и правильный исход. Он означает:
«рынок предлагает лучше, чем твоя цена, но ты просил не платить комиссию».
Дальше решает уже наш код, а не биржа.

## 4. Как принимается решение «пассивно или тейкером»

Живёт в `app/pricing.py`, функция `decide()`. Логика по шагам:

1. **Сторона.** `p(Up) ≥ 0.5` → ставим на `Up`, иначе на `Down`.
2. **Цена.** Всегда фиксированная — `LIMIT_PRICE = 0.49`. Не подстраиваемся под
   стакан намеренно: весь расчёт доходности в отчёте сделан именно для неё.
3. **Потолок.** Выше `MAX_ENTRY_PRICE = 0.55` не покупаем никогда. Модель
   переуверена (наклон калибровки 0.756): когда она обещает много, сбывается
   меньше обещанного, и правило «ставим, если прогноз выше цены» выше 55 центов
   ломается.
4. **Матожидание.** Если EV ≤ 0 — пропускаем час.
5. **Смотрим ask.** Если `ask > наша цена` — встречки по нашей цене нет, заявка
   спокойно ляжет в книгу. Шлём пассивно, на этом всё.
6. **Если `ask ≤ наша цена`** — мы бы исполнились тейкером. Считаем EV с
   комиссией и сравниваем **не с нулём, а с пассивным вариантом**.

Шестой пункт — самый важный и чаще всего понимается неправильно. Вопрос не
«выгодно ли это», а «выгоднее ли это, чем подождать». Условие в коде:

```python
ev_taker = expected_value(proba_up, best_ask, side, taker=True)
if ev_taker <= ev:
    ...  # всё равно шлём пассивно, отказ — нормальный исход
return Decision(..., cross=True)   # пересекаем книгу сознательно
```

Что получается на практике при p(Up) = 0.52:

| ask | эффективная цена с комиссией | Идём тейкером? |
|---|---|---|
| 0.47 | 0.4874 | **Да** — дешевле нашей 0.49 даже с комиссией |
| 0.48 | 0.4975 | Пограничный случай, обычно нет |
| 0.49 | 0.5075 | **Нет** — дороже, чем просто ждать |

Дешёвое предложение окупает комиссию, цена вровень с нашей — нет.

### Что происходит после отказа

Отказ не означает «пропустили час». В `app/runner.py`:

- **Быстрая серия** (`_place_until_resting`): пробуем заново каждые
  `RETRY_SECONDS = 5` секунд, до начала часа. Перед каждой попыткой **заново
  читаем стакан** и заново вызываем `decide()` — если ask ушёл вниз до уровня,
  который окупает комиссию, переключаемся на тейкера прямо посреди серии.
- **Медленный режим** (`retry_pending`): если серия не дала результата, час
  переходит в статус `PENDING` и попытка повторяется на каждом тике (раз в
  30 секунд) до конца часа.

Дедлайн — именно **начало часа** для первой серии, потому что признаки модели
заморожены на `CUTOFF_MINUTES = 2`: любая попытка внутри окна — это одна и та же
ставка, а вход после старта часа — уже другая, под неё модель не обучалась.

### Неприятная правда, которую показали данные

Мы проверили это на 723 рынках со стаканом и 863 наших ордерах. Результат:

| Что измеряли | Значение |
|---|---|
| Точность модели в целом | ~54.5% |
| Точность **заполнившихся** пассивных ордеров | **50.3%** |
| Точность **незаполнившихся** | 97% |

Читается это так: **пассивная заявка — бесплатный опцион, который мы дарим
контрагенту.** Она исполняется в основном тогда, когда рынок уже сдвинулся против
нас и продавцу стало выгодно нам продать. Когда мы правы — цена уходит вверх,
и нам просто никто не продаёт. Почти весь перевес модели живёт в сделках,
которые никогда не исполняются.

Час 2026-09-05 11:00 — ровно этот случай: ордер простоял весь час, не исполнился,
рынок закрылся `Down`, а мы ставили `Up`. Заявка спасла нас от убытка. Но по той
же механике она не даёт заработать, когда мы правы.

Отсюда следует: **менять цену входа бессмысленно** — маржа плоская на всей сетке
от 0.44 до 0.52. Проблема не в уровне цены, а в самом способе исполнения.

## 5. Сколько денег ставить: формула Келли

### Сама формула

Критерий Келли даёт долю банкролла, максимизирующую **темп роста капитала**
в долгую. Для бинарного контракта, купленного по цене `x` с вероятностью
выигрыша `q`, она сводится к очень простому виду:

```
f* = (q − x) / (1 − x)
```

В числителе — наш перевес в вероятности, в знаменателе — сколько мы выигрываем
на шейр. Если `q ≤ x`, формула даёт ноль или минус: **ставить нельзя**.

### Считаем для нас

Вход `x = 0.49`. Банкролл на счету — **$50**.

| Оценка точности | Откуда | q | f* | Риск на ставку | Шейров |
|---|---|---|---|---|---|
| 53.65% | walk-forward, 26 280 часов | 0.5365 | **9.12%** | $4.56 | 9.3 |
| 53.05% | нижняя граница ±0.60 | 0.5305 | 7.94% | $3.97 | 8.1 |
| 54.25% | верхняя граница | 0.5425 | 10.29% | $5.15 | 10.5 |
| **50.3%** | **фактические заполнения** | 0.5030 | **2.55%** | **$1.27** | **2.6** |
| 50.0% | честная монетка | 0.5000 | 1.96% | $0.98 | 2.0 |
| 49.0% | перевеса нет вообще | 0.4900 | 0% | $0 | 0 |

**Сейчас мы ставим 5 шейров = $2.45 = 4.9% банкролла.**

И вот тут вся суть. Ответ зависит от того, какой строке верить:

- Если верить walk-forward (9.12%) — мы ставим **примерно половину Келли**.
  Это классическая консервативная настройка, всё в порядке.
- Если верить фактическим заполнениям (2.55%) — мы ставим **почти вдвое больше
  полного Келли**. А переставка сверх полного Келли не просто рискованна, она
  **математически хуже** по темпу роста, чем правильная ставка.

### Во что это обходится

Логарифмический прирост капитала на одну ставку, `g = q·ln(1+f·b) + (1−q)·ln(1−f)`:

| Реальная точность | При оптимальной ставке | При нашей (4.9%) | В пересчёте на сутки (24 ставки) |
|---|---|---|---|
| 53.65% | +0.00433 | +0.00340 | **+8.2% в сутки** |
| 50.3% | +0.00034 | +0.00005 | +0.12% в сутки |
| 49.0% | 0 | −0.00125 | **−3.0% в сутки** |

Разброс огромный. Между «удваиваем счёт за неделю» и «сливаем 3% в день» лежит
разница в полтора процентных пункта точности, которую мы **пока не измерили**
с нужной надёжностью.

### Упирается в минимальный лот

`orderMinSize` у часовых рынков — **5 шейров**, меньше поставить физически нельзя.
Отсюда таблица «какой нужен банкролл, чтобы $2.45 были правильной ставкой»:

| Точность | Полный Келли | Половинный | Четвертной (рекомендуемый) |
|---|---|---|---|
| 53.65% | $27 | $54 | **$107** |
| 50.3% | $96 | $192 | **$384** |

При банкролле $50 и минимальном лоте $2.45 у нас **нет возможности поставить
меньше**, чем половину Келли по оптимистичной оценке. Вариантов ровно два:
либо довести банкролл примерно до **$110–120** и тогда 5 шейров станут честной
четвертью Келли, либо не трогать размер и понимать, что мы работаем на повышенной
дробности Келли ради сбора статистики.

### Практический вывод

1. **Размер ставки сейчас менять не нужно.** 5 шейров — минимум биржи, и он же
   примерно половина Келли по оптимистичной оценке. Это приемлемо.
2. **Увеличивать объём нельзя** до тех пор, пока перевес на заполнившихся
   сделках не подтверждён. По нашим расчётам для этого нужно около
   **6800 часов (~9.5 месяцев)** данных — сейчас есть заметно меньше.
3. Если банкролл вырастет до $110+, текущая ставка автоматически станет
   четвертной Келли, и это **правильное направление**: не увеличивать ставку,
   а увеличивать подушку под ней.
4. Келли предполагает, что `q` известна. У нас она **не известна** — поэтому
   считать надо по нижней границе доверительного интервала, а не по центру.

## 6. Полная логика бота: что происходит за час

Цикл крутится с тиком **30 секунд**. Один тик делает четыре вещи по порядку:
опрос заполнений → повторы неудавшихся постановок → резолвы → решение по
следующему часу.

### Расписание одного рынка (всё в UTC)

```
H − 120с … H − 25с   окно решения: первый тик внутри него ставит ордер
H − 120с … H         быстрая серия повторов каждые 5 секунд
H … H + 1ч           опрос заполнения каждые 30 секунд + события по WebSocket
H + 1ч + 60с         резолв, P&L, запись в базу, уведомление в Telegram
```

### Шаг за шагом

**1. Окно решения открывается за 2 минуты до часа** (`EARLY_SECONDS = 120`).
Почему заранее, а не ровно в H:00? Проверено переобучением: ранний вход ничего не
стоит по точности (52.86% против 52.72%), зато даёт запас времени на постановку.

**2. Проверки перед ставкой.** Не на паузе ли бот, не сработали ли лимиты
просадки (`DAILY_LOSS_LIMIT_USD = 40`, `MONTHLY_LOSS_LIMIT_USD = 100`),
принимает ли рынок ордера вообще.

Реальный случай: 2026-09-03, три часа подряд биржа отвечала
`503 trading is disabled` — рынок был закрыт на стороне Polymarket. Бот записал
часы как ошибочные и пошёл дальше, ничего не сломав.

**3. Признаки и прогноз.** Грузим минутки Binance, режем последнюю свечу на
`CUTOFF_MINUTES = 2` (ровно так, как модель обучалась), считаем 22 признака,
получаем `p(Up)`.

**4. Читаем стакан** по той стороне, на которую собираемся ставить, и вызываем
`decide()` — раздел 4 выше.

**5. Пишем в базу решение и снимок стакана** (таблица `quotes`) — ещё до того,
как узнаем результат постановки. Это наши исследовательские данные: по каким
ценам ордер в принципе можно было бы исполнить.

**6. Отправляем ордер.** Тип `GTD` — Good-Til-Date, со сроком жизни до конца часа
минус 30 секунд. Важная деталь устойчивости: **ордер умрёт сам, даже если бот
упадёт**. Никаких зависших заявок на бирже.

**7. Ждём исполнения — двумя способами сразу.**

### Что мы получаем по WebSocket

Два независимых канала (`app/ws.py`), оба в отдельном потоке-демоне:

- **`user`** — наши собственные ордера и сделки. Требует L2-кредов, которые
  CLOB-клиент выводит из приватного ключа детерминированно. Заводить руками
  ничего не нужно, **но в бумажном режиме канал не поднимается** — там нет
  торгового клиента, а значит и кредов.
- **`market`** — стакан по конкретным токенам, авторизация не нужна.

Событие приходит примерно так:

```
ws-user: подписка на 2 рынков, переподключение
ws-user: подписка отправлена (2 рынков)
```

Дальше при сделке прилетает событие `trade`. И вот **важное сознательное
решение**: объём сделки из события мы **не берём**. Событие говорит только
«по этому ордеру что-то произошло» — а сколько именно налили, мы спрашиваем
у биржи отдельно по REST.

Почему так. Форма события разная в зависимости от роли:

- исполнились **пассивно** → наш объём в `maker_orders[].matched_amount`,
  а верхнеуровневый `size` — это объём **всей сделки**, не наша доля;
- исполнились **агрессивно** → наш объём в верхнеуровневом `size`.

Разбирать эту двусмысленность в двух местах кода — гарантированный источник
ошибок в учёте. Поэтому WebSocket у нас — это **ускоритель, а не источник
истины**: он экономит до 30 секунд задержки, но цифры всегда приходят из REST.

Если сокет умрёт — опрос по REST раз в 30 секунд остаётся страховкой, и торговля
не останавливается. Канал сам переподключается с растущей паузой до 60 секунд.

**8. Час закончился.** Если ордер не исполнился — отменяем его и помечаем
`UNFILLED`. Если исполнился — ждём резолва.

**9. Резолв через час и минуту.** Смотрим на Binance: закрытие часа выше
открытия или нет. Дополнительно **сверяем с тем, что говорит Polymarket**.
Расхождение означает, что либо данные кривые, либо правило рынка изменилось —
и то, и другое надо заметить сразу. Такое было один раз, 2026-08-15:

```
15.08 12:00Z: Binance даёт Up, Polymarket Down — проверьте правило резолва
```

**10. Считаем P&L** по **реальной цене исполнения** и за вычетом фактически
уплаченной комиссии — не по цене заявки. Разница существенная: наш лимит 0.49
при живом предложении 0.47 покупается по 0.47, и если брать цену заявки,
результат систематически завышен.

**11. Уведомление в Telegram** с итогом часа, P&L за день и накопленной
статистикой.

### Три механизма защиты от дублей и падений

Стоит понимать явно, потому что это то, что позволяет спокойно перезапускать бот:

1. **Ордер живёт до конца часа** (GTD) — умрёт сам без нашего участия.
2. **На каждый час в базе ровно одна строка** — повторный запуск не удвоит ставку.
3. **При старте незакрытые рынки дорезолвливаются** — история не рвётся.

Плюс множество `_dispatched` в памяти: часы, по которым заявка уже уходила на
биржу. Защищает от того, что сбой посреди серии повторов поставит второй ордер
на тот же рынок.

## 7. Разбор одного реального часа целиком

Час **2026-09-05 12:00 UTC**, первый час после перехода в боевой режим.

```
11:58:25  runner  12:00:00+00:00 | bitcoin-up-or-down-september-5-2026-8am-et
                  | Up × 5 шейров по 0.49 [пассивно]
                  (p(Up)=0.5201, EV=+0.150$, риск 2.45$)
11:58:25  trader  ордер отправлен ... Up × 5 по 0.49 [пассивно] → 0x2271d7a3...
11:58:25  ws      ws-user: подписка на 2 рынков, переподключение
11:58:25  ws      ws-user: подписка отправлена (2 рынков)
```

Читаем построчно:

- **11:58:25** — это `H − 95 секунд`, попали в окно решения (открылось в 11:58:00).
- **p(Up) = 0.5201** — модель чуть склоняется к росту. Слабый сигнал, но нам и не
  нужен сильный: порога уверенности у нас нет, ставим на каждый час. Проверяли
  отбор по уверенности — выигрыш +$112 против шума ±$792, то есть неразличим.
- **EV = +0.150$** — считается как `0.5201 × 5 × 0.51 − 0.4799 × 5 × 0.49`
  = `1.3263 − 1.1757` = `+0.1506`. Комиссии нет, потому что мейкер.
- **[пассивно]** — значит `ask` был **выше** 0.49. Встречки по нашей цене не было,
  post-only-конфликта не возникло, заявка спокойно легла в книгу **с первой
  попытки** (в логе нет строк о повторах).
- **риск 2.45$** — максимум, который теряем: `5 × 0.49`.
- **ws-user переподписался** — список активных рынков изменился, канал
  переподключился, чтобы слушать именно этот рынок. Так работает `update_markets`:
  подписка задаётся при установке соединения, поэтому смена набора = переподключение.
  Для часового бота это раз в час, дёшево.

Дальше ордер заполнился мейкером по 0.49 на все 5 шейров.

### Для контраста — час 11:00 в бумажном режиме

```
12:00:27  runner  11:00:00+00:00: ордер не исполнился
12:01:29  runner  11:00:00+00:00 резолв Down (binance), ставили Up → +0.00$
```

Заявка `Up` по 0.49 простояла весь час и не нашла контрагента. Рынок закрылся
`Down` — то есть мы были **неправы**, и незаполнение спасло нас от `−2.45$`.

Это ровно тот механизм из раздела 4: рынок шёл вниз, значит `Up` дешевел, значит
никто не хотел продавать нам `Up` по 0.49 — они бы продали дешевле. А когда мы
правы и `Up` дорожает, продавец по 0.49 тем более не появляется.

**Опцион всегда исполняется против нас.** Это и есть главная нерешённая проблема
стратегии, и именно поэтому пункт 2 из выводов по Келли важнее всех остальных.

## 8. Краткая шпаргалка

| Вопрос | Ответ |
|---|---|
| Почему 0.49? | Точка безубыточности = цена входа. 0.49 против точности 53.65% даёт 4.65 п.п. запаса |
| Почему не выше 0.55? | Модель переуверена (наклон калибровки 0.756), выше 55¢ правило ломается |
| Почему post-only? | Комиссия тейкера = 1.8 п.п. требуемой точности, это треть нашего перевеса |
| Почему заявку отклоняют? | Лимитка «по 0.49» = «по 0.49 **или дешевле**». При ask ≤ 0.49 она пересекает книгу |
| Почему не переставить ниже? | 0.48 при ask 0.47 пересекает книгу точно так же. Лечь может только 0.46 и ниже |
| Когда идём тейкером? | Только когда EV с комиссией **выше** пассивного варианта. Практически при ask ≤ 0.47 |
| Что даёт WebSocket? | Сигнал «по ордеру что-то произошло» на 30 сек раньше. Цифры всё равно из REST |
| Сколько ставить по Келли? | 9.1% банкролла по walk-forward, 2.6% по фактическим заполнениям. Сейчас ставим 4.9% |
| Можно увеличить объём? | Нет, пока перевес на заполнившихся не доказан. Нужно ~9.5 месяцев данных |
