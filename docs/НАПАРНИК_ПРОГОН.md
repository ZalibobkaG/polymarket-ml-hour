# Трёхсуточный прогон

Продолжение [НАПАРНИК_УСТАНОВКА.md](НАПАРНИК_УСТАНОВКА.md) — установка уже
сделана. Здесь — как запустить бота, что происходит каждый час, что смотреть
и когда звать владельца.

---

## 1. Убедиться, что режим холостой

**Боевой режим включает только владелец.** Ваша задача — не трогать это, а
перед запуском убедиться, что режим действительно бумажный. Три способа
проверить, любой из них:

```bash
python main.py doctor
```
— смотрите на пункт 9, «РЕЖИМ РАБОТЫ»: должно быть `DRY_RUN = True` и рядом
«БУМАГА, ордера на биржу НЕ отправляются».

```bash
python main.py check
```
— первая строка вывода: `режим: БУМАГА (ордера не отправляются)`.

```bash
python main.py stats --days 1
```
— тоже первая строка: `режим: БУМАГА`.

Если хоть в одном месте видите «БОЙ» вместо «БУМАГА» — **не запускайте бота**
и сразу пишите владельцу. Сами переключать режим обратно не пытайтесь: это
`DRY_RUN` в `config.py` (или переопределение в `settings.toml`) — менять его
не ваша зона ответственности даже в холостом прогоне.

---

## 2. Запуск

Рабочий режим — бесконечный цикл, тик каждые 30 секунд:

```bash
python main.py run
```

**Должно получиться:** в терминале и в `logs/bot.log` появится строка вида
`loop started, mode PAPER, tick 30s`, дальше — тишина до ближайшего окна
решения (см. раздел 3).

**Чтобы оставить работать надолго:** в самом проекте нет готового скрипта
автозапуска или службы — это обычный процесс `python main.py run`, который
должен просто продолжать работать. Практически это значит одно из:
- оставить окно терминала открытым и не закрывать его (самый простой
  вариант, но остановится при закрытии окна, выходе из системы или
  перезагрузке);
- на Windows — создать задачу в Планировщике заданий (Task Scheduler) с
  триггером «При входе в систему» или «При запуске», которая запускает
  `.venv\Scripts\python.exe main.py run` с рабочей папкой — папкой боевой
  копии;
- на Linux — `screen`/`tmux`/`nohup`, либо служба systemd. Ни один из этих
  вариантов не входит в код проекта, выбор конкретного инструмента — не
  вопрос логики бота.

**Что будет при перезагрузке машины:** процесс бота сам не перезапустится
(если только вы не настроили автозапуск, см. выше) — его нужно будет
поднять вручную той же командой. Поднимать его безопасно в любой момент:
- на каждый час в базе ровно одна строка, повторный запуск не поставит
  вторую ставку на тот же час;
- лимитная заявка выставляется с типом GTD и сроком жизни до 12-й минуты
  часа — она снимется сама биржей, даже если бот не работал весь этот
  промежуток;
- рынки, которые остались нерезолвленными, бот дорезолвит сам при
  следующем запуске — история не рвётся.

Если после перезапуска что-то выглядит не так — не пытайтесь чинить руками
базу или логи, сразу к владельцу.

## 3. Что происходит каждый час

Расписание одного часового рынка (всё время — UTC):

```
H − 2 мин    решение (сторона от модели) → лимитная заявка по 0.51
H + 12 мин   если заявка не исполнилась целиком — добор по рынку,
             не дороже 0.55
H + 1ч 1мин  расчёт исхода, запись P&L, уведомление
```

Ниже — настоящие строки из `logs/bot.log` этого же бота (не придуманные,
взяты из реального холостого прогона).

### H − 2 минуты: решение и заявка

```
2026-09-11 19:59:10.579 | ℹ️ INFO     | runner:_decide_and_order:233 | 2026-09-11 20:00:00+00:00 | bitcoin-up-or-down-september-11-2026-4pm-et | Up × 10 шейров по 0.51 [лимиткой в книгу] (p(Up)=0.5429, EV=+0.329$, риск 5.10$)
2026-09-11 19:59:12.535 | ✅ SUCCESS  | trader:place:133 | [paper] order bitcoin-up-or-down-september-11-2026-4pm-et Up × 10 at 0.51 [GTD] (paper-2026091120-up-limit)
```

Читается так: на час 20:00 UTC модель дала `p(Up)=0.5429` (чуть больше
половины) → ставим `Up`, 10 шейров по 0.51, риск 5.10$. Заявка легла в
книгу («лимиткой в книгу» — значит аск в этот момент был выше 0.51, сразу
не исполнилась). `[paper]` в строке ниже — метка бумажного режима, в
боевом её не будет.

### H + 12 минут: добор, если не исполнилось целиком

Тот же самый час 20:00 UTC — лимитка за 12 минут так и не встретила цену
0.51, и на 12-й минуте бот снял её и проверил рынок для добора:

```
2026-09-11 20:12:51.127 | ℹ️ INFO     | trader:cancel_confirmed:163 | [paper] cancel paper-2026091120-up-limit
2026-09-11 20:12:53.621 | ℹ️ INFO     | runner:_finish_cross:642 | 2026-09-11 20:00:00+00:00: аск 0.80 выше потолка 0.55 — не добираем
2026-09-11 20:12:53.622 | ⚠️ WARNING  | runner:_settle_after_cross:652 | 2026-09-11 20:00:00+00:00: nothing filled — аск 0.80 выше потолка 0.55 — не добираем
```

Читается так: неисполненный остаток лимитки сняли (`cancel_confirmed`),
посмотрели лучший аск для добора — 0.80, это выше потолка `TAKER_MAX = 0.55`
— и решили не добирать вовсе. Час остался без ставки (`filled_shares = 0`,
статус `unfilled`). Это ровно тот случай «аск выше 0.55» из нормы в разделе
5 — не ошибка, а штатный отказ по цене.

Второй штатный отказ, «пустой стакан» (лучшего аска для стороны ставки нет
вовсе), в этом конкретном прогоне ещё не встретился — в коде это
`runner.py`, функция `_cross_one`, строка со `стакан пуст — не добираем`.
Выглядеть он будет так же, как строка выше, только с этим текстом вместо
«аск … выше потолка».

### Конец часа: расчёт исхода

На момент, когда писался этот документ, ставка на час 20:00 UTC (пример
выше) ещё не дошла до расчёта — он происходит примерно через час после
решения, а не сразу. Вместо того чтобы придумывать строку, вот точный
формат из кода (`app/runner.py`, функция `resolve_pending`, за строкой
`log_fn("{} resolved {} (via {}), bet {} → {:+.2f}$", …)`) — в фигурных
скобках то, что подставится по факту:

```
{дата и час рынка} resolved {Up/Down — фактический исход} (via {binance/polymarket}), bet {Up/Down — на что ставили} → {P&L со знаком}$
```

Значок и цвет строки говорят сами за себя: зелёный ✅ SUCCESS — угадали,
жёлтый ⚠️ WARNING — не угадали. Проигрыш здесь **не ошибка** — это
нормальный, заранее заложенный в стратегию исход (см. `app/log.py`):
тревожиться стоит по числам из раздела 5, а не по цвету отдельной строки.
Источник исхода — обычно `binance`; `polymarket` — запасной вариант, если
подтвердить исход по Binance не удалось.

## 4. Что смотреть раз в сутки

```bash
python main.py stats --days 1
```

Печатает четыре числа и разбивку отказов: долю часов, где принято решение
ставить; долю часов, где заявка исполнилась; долю мейкерных исполнений
среди исполненных; среднюю цену входа — и отдельно отказы по причинам с
количеством каждой. Разбирать эти цифры не нужно — просто сверяйте их с
нормой ниже.

---

## 5. Норма за прогон

| Показатель | Норма |
|---|---|
| решение принято | 100% часов |
| заявка исполнилась | около 93% часов |
| доля мейкера | около 55% |
| средняя цена входа | около 0.505 |
| отказы | только двух видов: пустой стакан и аск выше 0.55 |

В выводе `python main.py stats --days N` эти два вида отказов подписаны
«пустой стакан» и «аск выше потолка добора» — это то же самое, что «аск
выше 0.55» в таблице выше (0.55 — значение `TAKER_MAX`).

**Расхождение больше двух процентных пунктов по любой строке — остановиться
и сообщить владельцу, самостоятельно не чинить.** Это касается и появления
отказа с причиной, которой нет в этих двух — см. раздел 10.

## 6. Признаки неполадок

Все сообщения уровня `❌ ERROR` в логе требуют внимания владельца — по
задумке проекта (см. `app/log.py`) до уровня ERROR доходит только то, что
не является нормальным ходом торговли. Конкретно в холостом прогоне
реально могут встретиться (в фигурных скобках — то, что подставится по
факту: дата, час, текст конкретной ошибки — это не буквальный текст лога):

```
{дата}Z: hour lost — {причина}
```
— час полностью потерян: ни ставка не встала, ни было понятной причины
отказа за окно решения. Строка сопровождается уведомлением «Час пропущен
из-за сбоя».

```
resolution rule changed or market not found: {ошибка}
```
— автоматическая суточная проверка не смогла подтвердить, что рынок
по-прежнему резолвится тем же способом (Binance, close ≥ open). Может
значить, что Polymarket поменял правило резолва.

```
{дата}Z: Binance даёт {X}, Polymarket {Y} — проверьте правило резолва
```
— источники разошлись в исходе конкретного часа. Такое уже случалось один
раз (см. `docs/how_orders_work.md`) и требует ручной проверки.

Одна строка, которая выглядит как предупреждение, но сама по себе **не**
является проблемой:

```
no L2 creds — user channel not started, fills are tracked by REST polling
```
— это ожидаемо при каждом запуске в холостом режиме без ключей биржи в
`.env`: бот и не должен их иметь на этом этапе, просто узнаёт об
исполнении по опросу раз в 30 секунд вместо мгновенного уведомления.

Отдельно стоит не перепутать два похожих по смыслу, но разных по важности
предупреждения о неисполнении:

```
{дата}: nothing filled — {причина}
```
— это штатный конец часа без ставки (пример в разделе 3): добор состоялся,
но решил не добирать по одной из двух известных причин. Само по себе не
проблема, ожидаемо примерно в 7% часов (см. норму в разделе 5).

```
{дата}: order not filled
```
— **это другое и заметно реже нормальное**: по докстрингу самого кода
(`app/runner.py`, `_close_unfilled`) сюда доходит только то, что добор
вообще не успел отработать за весь час целиком — например, бот не работал
все 12–20 минут окна добора. Если видите именно эту строку — это не одна
из двух известных причин отказа, см. раздел 10.

## 7. Чего не менять ни при каких обстоятельствах

`LIMIT_PRICE`, `POST_ONLY`, `CROSS_AFTER_SECONDS`, `TAKER_MAX`,
`MAX_ENTRY_PRICE`, `CUTOFF_MINUTES`, а также саму модель и комплект модели
(`poly_hourly_kit/`, команда `python main.py retrain`). Эти значения
получены замером на реальном стакане (см. `config.py` и
`docs/how_orders_work.md`) — любое изменение обесценивает прогон, даже если
кажется безобидным.

**Что менять можно и как.** `SHARES` (размер ставки), лимиты убытка
(`DAILY_LOSS_LIMIT_USD`, `MONTHLY_LOSS_LIMIT_USD`) и `COIN` — через
`settings.toml` в корне папки бота (в git не попадает, при обновлении
репозитория не перезапишется):

1. Если файла `settings.toml` ещё нет — скопировать `settings.example.toml`
  в `settings.toml`.
2. Вписать туда только нужный ключ с новым значением, остальное не трогать.
3. Проверить: `python main.py settings` — покажет итоговое значение
  каждого параметра и источник, ничего не запуская.
4. Перезапустить бота (`main.py run`) — настройки читаются один раз при
  старте, на лету `settings.toml` не подхватывается.

Размер ставки (`SHARES`) можно менять и без перезапуска — командой
`/shares` в Telegram (раздел 8): подействует со следующего решения,
открытые позиции не тронет.

## 8. Команды Telegram

Доступны только пользователям из `TG_ALLOWED_USER_IDS`. Полный список (тот
же, что в ответе на `/help`):

- `/menu` — меню с кнопками (дублирует команды ниже).
- `/status` — что происходит прямо сейчас: пауза или работа, время до
  следующего решения, P&L за сутки и всего, открытые позиции.
- `/stats` — статистика с кнопками: за 30 дней, три графика (equity,
  уверенность модели, угадывания) и разбор, как каждый график считается.
- `/log` — прислать `logs/bot.log` файлом в чат (`/log 500` — последние 500
  строк, `/log all` — файл целиком).
- `/shares` — показать или изменить размер ставки (`/shares 15`).
- `/pause` — не делать новых ставок; начатое доводится до резолва.
- `/resume` — снять паузу.
- `/stop` — остановить бота (см. раздел 9).
- `/help` — этот же список текстом.

---

## 9. Как остановить бота штатно

Два равнозначных способа:
- в Telegram набрать `/stop` — остановится сразу;
- в терминале, где запущен `python main.py run`, нажать `Ctrl+C`.

Оба приводят к одному и тому же: цикл останавливается, соединения
закрываются. **Уже выставленная заявка при этом не отменяется** — и это не
забытый случай, а часть конструкции: лимитная заявка стоит на бирже с
типом GTD и снимется сама к 12-й минуте часа независимо от того, работает
бот или нет; открытая позиция резолвится на бирже сама, а её исход
запишется в базу при следующем запуске бота. Руками ничего снимать не
нужно.

## 10. Когда звать владельца

- любое отклонение из раздела 5 больше двух процентных пунктов по любой
  строке;
- любая ошибка, где фигурируют деньги (баланс, комиссия, P&L) и она не
  выглядит как обычный проигрыш ставки;
- любое срабатывание дневного или месячного лимита убытка (в логе — «дневной
  убыток … достиг лимита» / «месячный убыток … достиг лимита … требуется
  ручная проверка модели»);
- любой отказ с причиной, которая не «пустой стакан» и не «аск выше 0.55».

В любом из этих случаев — не чинить самостоятельно, написать владельцу с
описанием и, если возможно, приложить вывод `python main.py stats --days 1`
и последние строки `logs/bot.log`.

---

## 11. Что прислать владельцу в конце прогона

- файл(ы) `logs/bot.log` (и любые `logs/bot.*.log`, если за три дня прошла
  смена суток по UTC — ротация ежедневная);
- файл базы `data/bot.db`;
- вывод команды `python main.py stats --days 3`.
